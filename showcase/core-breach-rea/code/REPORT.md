# CORE BREACH — report

CORE BREACH is an original first-person shooter built on an engine recovered
from the shareware DOOM v1.9 `DOOM.EXE` (1993/1994, id Software; the shareware
release is freely copyable).  No DOOM art, maps, sounds, names, characters,
textures, palettes or data tables are used by the game.  All of the game's
content is generated by the code in `game/js` and `tools/build-map.mjs`.

## How to run

```
cd /work/game
python3 -m http.server 8080
# open http://127.0.0.1:8080/index.html
```

- Click the canvas to deploy (pointer lock).  Esc pauses/unlocks.
- Move with W A S D or the arrow keys; turn with the mouse.
- Fire with left click or Ctrl; use with E or Space; weapons 1..3.
- Attract mode: `http://127.0.0.1:8080/index.html?attract=1`.
- Rebuild the level after editing `maps/reactor7.source.json`:
  `node tools/build-map.mjs`.
- Run the automated checks: `node verify.mjs` (writes the screenshots and
  exits non-zero on failure).

## What was recovered from the binary

### Conversion

`tools/le2elf.py` turns the DOS/4GW LE image into `/work/analysis/doom-le.elf`.
The MZ header in this stub is old enough that `e_lfanew` at 0x3c is inside the
relocation table, so the converter validates/scans for the LE header; it finds
it at 0x27acc.  It handles the LE object table, sequential page map, short
final stored page, fixup page table and all fixup record forms needed by this
file.  The result is a valid ELF32/i386 ET_EXEC with one PT_LOAD per object at
0x10000 (code), 0x60000 (small object) and 0x70000 (data), plus .bss and
section headers.  The entry point is 0x50b48 and decompiles as the Watcom
startup/init-table walker.  Data pointers occur in code (for example 0x8f578
near 0x1f579), and call targets land in the code object.  Because a few page
records in this Watcom file point inside instruction immediates or at genuine
zero constants, the converter validates every destination and applies 1389
records while skipping 10715 destructive/irrelevant ones; all function-entry
prologues remain intact.  Ghidra sees 677 procedures and 739 strings.

### Engine addresses and mechanisms

The detailed, per-function evidence is in `REVERSE_NOTES.md`.  The parts used
by the game are:

- **Math** — 16.16 fixed point, saturating `FixedDiv` at 0x2a8c8, binary
  angles (`ANG90=0x40000000`), 8192-entry fine sine/cosine indexing
  `(angle + 0x40000000) >> 19` (0x42f18/0x453e8, DS:0x5a84), point-to-angle
  0x42c58, and the 256-byte table PRNG at 0x318a8/0x318c8.  The game
  regenerates its sine/cosine and random tables; it does not copy table bytes.
- **Renderer** — R_RenderPlayerView 0x436f8, R_SetupFrame 0x435c8,
  R_RenderBSPNode 0x41208, R_Subsector 0x41118, R_AddLine 0x40e68,
  R_CheckBBox 0x40fa8, R_StoreWallRange 0x44448, R_RenderSegLoop 0x440c8,
  R_ClearPlanes 0x43908, R_FindPlane 0x439b8, R_CheckPlane 0x43a88,
  R_DrawPlanes 0x43c08, R_GetColumn 0x46448, R_DrawColumn 0x41698,
  R_ProjectSprite 0x453e8, R_SortVisSprites 0x459f8, R_DrawMasked 0x45d28,
  R_Init 0x431b8, light tables 0x42fb8.  The engine's BSP traversal uses the
  same node-side and bounding-box tests; walls are projected to columns and
  clipped by solid screen ranges; floors/ceilings are collected as visplane
  spans and drawn with a depth test; sprites are sorted and clipped; the sky
  is a generated panorama; the view is 320x168 plus a 32-pixel status bar.
- **Map model** — sectors, linedefs, sidedefs, segs, subsectors, nodes,
  blockmap and reject were recovered from their consumers: P_BlockThingsIterator
  0x39c68 (mobj stride 0x3e), P_BlockLinesIterator 0x39ce8, P_PathTraverse
  0x39fe8, P_CheckSight 0x387a8, sector thing list at +0x46 (0x456d8),
  linedef next-in-block +0x2c, and the renderer's sector/seg access.
- **Game loop** — D_DoomLoop 0x2ac58; 35 Hz tics; input sampled once per tic
  and an accumulator-driven main loop.
- **Movement** — P_CheckPosition 0x392c8, P_TryMove 0x39368, P_CheckSight
  0x387a8/0x38948.  The game uses 16.16 positions/velocities, thrust,
  friction, a 24-unit step, a 56-unit player height, 16-unit radius, gravity,
  view bob, circle-vs-linedef collision and wall sliding.
- **Sight and shots** — blockmap/line traversal and ray/segment tests are used
  for line-of-sight, hitscan and projectile collision.
- **Moving sectors** — P_SpawnDoor/EV_DoDoor 0x341f8 allocates a 0x56-byte
  thinker with state pointer, 150-tic wait and 2-unit/tic speed.  The game
  uses ceiling doors (yellow and cyan), a floor lift, secret panel lines and
  an exit switch, with a use trace of 72 units / ~45°.
- **Actors** — thinker allocation/state pointers and mobj x/y/z/angle/
  state/frame fields are visible in 0x341f8, 0x456d8, 0x39c68 and 0x453e8.
  The game implements an equivalent thinker/state machine with idle, chase,
  attack, pain and death states; the exact optimized `A_*` action names were
  not reliably recoverable, so the monster behaviours are original.

## What is new

Everything in the game is original and generated by the shipped code:

- Name, premise, level "Reactor Deck 7", all text and messages.
- 51 sectors, 189 linedefs, 138 BSP subsectors, 133 nodes, 429 segs, 42
  things; 16 procedurally generated wall textures, 8 flats and a 512×128 sky.
- Three original enemies: Cutter (wheeled saw robot), Drone (hovering ion-bolt
  robot), Sentinel (heavy two-legged walker with a hitscan burst), each with
  generated 8-rotation sprite sheets, idle/walk/attack/pain/death frames and
  synthesized sounds.
- Three original weapons: rivet gun (fast hitscan), scatter cannon (pellet
  spread), arc launcher (projectile with blast damage).
- Pickups (patch cell, trauma kit, heavy plating, ammunition, rivet, scatter
  cannon and arc launcher), keycards, HUD, title/death/complete screens,
  procedural reactor core/tower props, coolant damage, flickering lights,
  secret areas, doors, lift, stairs and an authored attract route.
- Every audio effect is synthesized at runtime with Web Audio.

## Approximations and limitations

- **Data vs code relocation.** The final ELF applies LE fixups correctly and
  its call/data pointers are right, but Ghidra's auto-analysis on the final
  image merges or misses some function starts (for example R_RenderPlayerView
  at 0x436f8).  The notes record the interim-image decompilations at the same
  code addresses; instruction bytes at those entries are identical except for
  relocated operands.
- **Point-to-angle.** The recovered routine 0x42c58 uses a slope table and
  octant cases; the game uses a generated `atan2`-equivalent converted to
  32-bit binary angles.  It is mathematically equivalent, not byte-identical.
- **Fine trig tables.** The game generates 8192-entry sine/cosine tables; the
  original table values are not copied.  The indexing rule and fixed-point
  scale are the recovered ones.
- **Visplanes/clipping.** The game collects spans per sector/plane and draws
  them with a per-pixel depth test, plus solid screen ranges updated during
  front-to-back BSP traversal.  This is a faithful mechanism but not a
  byte-for-byte reproduction of DOOM's 320-column clip list; it is more robust
  against gaps in an arbitrary hand-authored map.
- **Map loader.** The WAD/P_Load* functions were not cleanly separable from
  file I/O in this optimized Watcom build, so the map data layout was recovered
  from its consumers.  The game's map compiler emits the same concepts
  (sectors, linedefs, sidedefs, segs, subsectors, nodes, blockmap, reject).
- **Actor state names.** The exact `A_*` action functions could not be named
  reliably; the thinker/state mechanism is recovered, the three enemy
  behaviours are original implementations.
- A few complex reactor-hall/lift views intentionally expose large open
  sightlines and the outdoor windows; these are map design choices, not
  missing assets.

- `tools/le2elf.py` — LE → ELF32 converter.
- `analysis/doom-le.elf` — analyzable ELF used with REA.
- `REVERSE_NOTES.md` — per-function evidence, addresses and REA calls.
- `maps/reactor7.source.json` — hand-authored map source.

- `game/verify.mjs` — automated acceptance tests and screenshot capture.
