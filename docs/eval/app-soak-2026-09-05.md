daemon from the main build plus #2156 started detached from the home directory before the app, the app driven over
the Chrome DevTools Protocol like a user (textarea, send button, the + menu), with the preload API for state and
health. Driver and scenarios: `soak/soak.mjs`, `soak/scenarios/*.txt`; one JSONL record per prompt.

## 2026-09-06: the production bundle, a bypass session, and a daemon that died

The dev build had carried the renderer memory question (#183), so the second day ran the production bundle
(`electron-vite build`, `out/`) against the daemon rebuilt on main with #2172 to #2183. A fresh Electron profile
starts on the first-run view with no sidebar, and the sidebar's project rows come from the renderer's own
localStorage, not from the daemon's sessions; the driver gained a `prime` command for that.

The first chat run in bypass mode died at its second prompt, and the failure was a chain. `npm install` needs the
network; the model asked for `sandbox_permissions: require_escalated`; bypass mode had set the approval policy to
`never` while leaving the sandbox at `workspace_write`, so the request was denied with "sandbox escalation requires
approval, but approval policy is never" (F44). The model retried the identical call three times, the repeat guard
refused the fourth in the post-stream pass while the streaming dispatch path had already started it, and one call id
got two results (F43). The rollout's live tool-pair validator rejected the second as a duplicate, and from then on every
prompt on the session opened a turn that failed on its own user message four seconds later, while the app's banner
said the daemon gave no reason (#2163). Four fixes: #2184 (one result per refused call), #2185 (bypass grants the
sandbox request the way an approval would), #2186 (a blocked history refuses the prompt with the reason), desktop
#188 (the banner shows the abort reason).

The second run, on a skills scenario, met the class the whole phase exists for. Fifty-four minutes into its life,
holding one live turn whose last command was an `ls`, the daemon exited. No line in its log, no crash report, no OOM
snapshot, nothing in the system log (F46). The production app noticed the closed connection and autostarted a
replacement in three seconds, and the replacement's recovery resolved the interrupted turn's four open tool calls twice:
the bootstrap replay closed them with persisted "interrupted" results, then the durable resume paired the same calls
with its own halt results and persisted those too, so the session's history was blocked by a duplicate exactly like
F43 (F45). The one file that would have held the old process's last words, the spawn stderr capture, had been
truncated by the spawn that replaced it. #2187 makes the resume skip calls the replay already closed; #2188 keeps the
previous capture as `daemon-spawn-stderr.prev.log`, so the next silent exit leaves evidence. The cause of the exit is
open.

A restart on this home is not free either: with 320 sessions on disk the daemon comes up at 1.4 GB RSS and takes about
half an hour to settle back to the 220 to 380 MB it holds while idle (F42). It does settle.

Renderer memory on the production bundle: the runs above were too short to answer #183 (two real turns each before the
session broke); the production renderer has none of the 1.32 million `performance.measure` entries the dev build
accumulated, and sat at about 200 MB RSS with a stable 3,900-node DOM across those turns. The measurement continues on
the rebuilt daemon, where a bypass session survives `npm install`.

## 2026-09-06, evening: the daemon exits, traced

The daemon died a third time, at 16:22Z during the swarm rerun's second prompt, and this time it died with the heartbeat
file (#2216) and a 10 s pid sampler watching: a healthy beat 6 s before (397 MB, 2 ms event-loop lag), memory flat at
390 MB, then nothing. That fixed the class of the exit. Crash reporting works on this machine and captures node aborts, and
it wrote no report for any of the three dead pids, so no crash signal. The #2203 handlers write synchronously to the
appending log and wrote nothing, so no SIGTERM, SIGINT, SIGHUP and no `process.exit`. Memory never approached the heap
cap. The only termination that leaves no report and runs no handler is SIGKILL. Every kill in AgenC was then read and
excluded: the sandbox supervisor's group kills cannot reach a session-leader daemon, the failpoints are test-only, the
autostart takeover never signals on macOS, the desktop bridge signals only on app shutdown, and no kill command was run by
the driver, by any soak agent, or by the second agent working on the same machine (its matches were fixture source it was
writing). What remained fit everything: the macOS memory-pressure killer, on a host whose swap was 90 to 95 % full while
this daemon, the desktop app and the other agent's core builds ran together, with a `JetsamEvent` from 2026-09-03 on the
same machine showing that killer terminating node and AgenC processes. The deaths clustered after the driver set bypass
on a live session and sent the next prompt because that is the daemon's heaviest work. The finding, then, is about the
host, not the daemon; the product items it leaves are the lost turn and the recovering replacement (F66, #2225, #2226).

A 40-prompt single-session coding run started afterwards on the same daemon as the primary-path endurance check and is
recorded in the runs table when it ends.

## 2026-09-06, night: the 40-prompt session

The primary path, one chat session running the 40-prompt ledgerlite scenario end to end through the app, held for
3 h 54 min without a failure: 37 prompts completed, 3 were cut by the harness's own 900 s step budget while the model was
still working (the rollout shows steady activity in each window, with the longest silence a single 179 s model call), and
the daemon that started the run was still the daemon at the end, 4 h 31 min old, between 133 and 655 MB. No reconnect,
no turn error, no permission stall.

The run found one defect of the kind that matters most. Both times the driver pressed Stop the turn aborted at once, and
nine seconds later the daemon started a new turn that nobody asked for: the seed was a receipt from a verifier agent the
model had spawned and closed earlier, delivered through the parent's mailbox, and `requestParentFollowupTurn` turned it into
a turn with no notion that the user had just stopped. The model saw its half-finished work in the history and resumed it,
for eighteen minutes the second time, with edits, commands and another spawned agent, while the composer stayed blocked
(F70, #2236). The fix, merged the same night as #2237, latches a user stop on the session until the next user message and
holds child receipts in the mailbox for that turn.

The session's growth also showed on the daemon: the rollout reached 26 MB and each compaction bookkeeping scan of it, a
whole-file read, grew from 64 ms at the start to 1.2 s at the end (#2229); the project's state database stood at 693 MB
before the run (#2228, now bounded by the 30-day default of #2235).

After the run, the daemon under test was killed with SIGKILL while a turn had a command in flight, to see the recovery
end to end with the fixes of the day in place. Two things followed. The kill itself was recovered as designed once a
daemon was back: hydrating the session in the app replayed the rollout, synthesized the missing abort, restarted the turn
and resumed it from its checkpoint with the halted `write_stdin` named, and the app showed both lines (desktop #195); but
the resumed turn ran without an approval resolver, so `write_stdin` and `exec_command` were refused and the model wrapped
up instead of finishing (F72, #2239). Before that, though, no daemon could come back at all: an hour earlier the
retention sweep, enabled on this home with a one-day window, had removed a day-old session whose run still held a pending
effect review, and startup recovery treats a pending review without journal evidence as fatal, so every replacement
daemon died during recovery and the app looped on autostart with a clear message (thanks to #2233). No CLI path could
clear it; the home was repaired by hand in the state database (F71, #2238). Two fixes followed the same night: the sweep
keeps such sessions (#2240) and recovery quarantines the run and starts instead of refusing (#2241). With the 30-day
default of #2235 this would otherwise have reached every long-lived install.

## Where this leaves the phase

The question was whether a user can run the agent for hours through the desktop app without a bug or a failure. After two days the answer splits by mode.

- **Chat.** Yes, on the rebuilt daemon: the closing run passed fourteen prompts in a row on the daemon with every fix, and what ended it was a provider outage plus F60; the rerun of the last six prompts then passed on the rebuilt daemon, so the whole 20-prompt scenario has passed on the daemon with every fix. A bypass session installs packages, runs its tools and keeps its history; the failures that ended sessions on day one (a duplicate tool result, a denied escalation, a session gated by an undecorated error) are fixed and merged. The renderer holds about 200 MB across turns on the production bundle (F50); the daemon holds 450 MB after two and a half hours with 333 sessions on disk (a restart costs 1.4 GB for half an hour, F42).
- **Plan mode.** Enforced end to end (F51), but not usable for long at xhigh on this provider: both plan prompts spent thirty minutes without presenting a plan, the first because the session crossed the context limit and its compaction failed on a network blip that was never retried (F55, fixed in #2196), the second in a stream that produced 30 tokens in 25 minutes (F52). A stop during that state took three minutes to land (F56, #2197).
- **Swarm.** The stance works: one prompt fanned out to 27 agents that ran for thirty minutes without a failure (F57). Stopping a swarm of that size is slow, and the driver's cap cut the run before it finished, so its result is not measured. On the daemon with the day's fixes, swarm-5 passed all six swarm prompts in 1 h 14 min on the daemon that had just run goal-13, with no error, no failed agent and no reconnect; the prompt after the fan-out, lost twice before to daemon deaths, passed.
- **Goals.** The runner completes end to end (goal-6 goal 3, goal-7 goal 1). On the daemon with the day's fixes, goal-13 completed five of six goals end to end on one daemon in 2 h 47 min with no reconnect; the sixth exposed that a failed verification's report never reached the retry (F73), fixed in #2245. With that fix in the daemon, the retry loop converges: goal-15's goal 5 failed verification and finished anyway, and goal-16 reran the goal that had never completed, fixing the bug its verifier named in 20 tool calls and passing re-verification in 11.4 minutes against 16.9 for the blind first pass. Its failures are the provider's: a verify agent's connection error (F41) and plan attempts that timed out; the rebuilt daemon carries the classification and cap-reset fixes for both, and the retest (goal-8) passed verify on the rebuilt daemon and then failed in review because the reviewer role's slug was sent to the provider as a model id (F58).
- **Skills and plugins.** Marketplace install, uninstall and update reload the daemon (#181); the id mismatch on uninstall is fixed (#2176); a skills scenario ran until the daemon under it died.

What still breaks a long session, in order of what it costs the user:

1. The daemon can be killed by the host (F46). Three silent exits were an OS memory-pressure SIGKILL while the soak daemon, the desktop app and a second agent's core builds shared a 16 GB machine with swap 90 to 95 % full; no AgenC path was involved. The heartbeat (#2216) now tells that death apart from a crash in seconds, and status describes the recovering replacement (#2226). What the product still lacks: the interrupted turn is lost rather than resumed after the replacement comes up, and the replacement's recovery spike (about 1.3 GB) is itself a target on a saturated host (#2225).
2. A provider stream that goes quiet holds the turn until the user presses stop, and the app cannot tell a stalled stream from long reasoning (F52). A soft "no output for N minutes" signal and a provider keepalive check are the open design; a hard default deadline would cut real high-effort reasoning.
3. An error result from a side-effecting tool that carries no effect disposition gates the whole session behind `/resolve` (F49, #2190). Every built-in tool a coding or swarm session uses in normal work now decorates its pre-effect refusals (#2189, #2191, #2193, #2195); the tools that report by throwing still need the thrown-error brand.
4. A daemon restart that interrupts a turn recovers it, but until #2187 the two recovery writers duplicated a result and blocked the session (F45). After a restart, a session blocked in the old process reads healthy again (F54).
